## Design

**`docs/design/breakpoint-prototype/` is the source of truth for tokens, design decisions
and layout.** Consult it before styling anything. The brief that produced it is
`docs/design/initial-design-prompt.md`.

| File                            | What it settles                                                                                                                        |
| ------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `globals.css`                   | The tokens. A `--bp-*` application layer plus shadcn's semantic names mapped on top of it, so copied component source works unmodified |
| `Breakpoint Directions.dc.html` | The two candidate answers to "how does a tool frame content it does not own", and why the framed one won                               |
| `Breakpoint Prototype.dc.html`  | The surfaces and their states                                                                                                          |
| `Breakpoint Tokens.dc.html`     | The token reference, including the pane palette over its three worst-case backgrounds                                                  |
| `_ds/nocturne-*/`               | The design system it was derived from                                                                                                  |

Standing rules that came out of it:

- **Never invent a token.** If a value is missing, add it to `globals.css` first, then use
  it. No raw hex, no ad hoc pixel values in components.
- **Chrome is only drawn on ground we own.** Error, crash, agent presence, off-screen and
  scheme mismatch are all rim-and-header events. The single exception permitted to draw
  over a page is the transient inspect highlight, because it has to register to an element
  box to mean anything.
- **Overlay strokes counter-scale.** Set `--bp-zoom` on the canvas; anything drawn over a
  pane uses `--bp-stroke-overlay`, so it stays 1.5 screen px at any canvas zoom.
- **Pane identity comes from `--bp-pane-1` … `--bp-pane-10`.** Fixed lightness and chroma,
  separated by hue alone, so the set survives rasterising into a composite screenshot.
  Never colour a pane any other way.
- **Pane headers hold their screen size** and degrade through tiers as the pane narrows;
  they are clipped by their own pane so a header can never claim width it does not have.

## UI components

**shadcn/ui components are only ever generated by the CLI. Never write one by hand.**

```
npx shadcn@latest add <component>
```

`src/renderer/src/index.css` is CLI output in structure — the imports, `@custom-variant`
and `@theme inline` block. Its token values are mirrored from the design prototype's
`globals.css`, which is the source of truth. Change them there first.

Components land in `src/renderer/src/components/ui/`. Once generated they are ours to
tighten to devtools density (PRD 8.2), edited in place rather than wrapped at each use
site. Re-running `add` on an existing component needs `--overwrite` and will discard
those edits.

The primitive layer is **Base UI** (`@base-ui/react`), style `base-nova`, and `cn` comes
from the `cn` package rather than a local `lib/utils`. Both are recorded in
`components.json`.

### Known friction: `init` does not detect electron-vite

`shadcn init` verifies the framework by looking for a `vite.config.*`, and this project
uses `electron.vite.config.ts`. It fails with "We could not detect a supported framework".
`add` is unaffected and needs no workaround.

If `init` ever has to run again, drop a stub `vite.config.ts` at the repo root, run it,
then delete the stub. The paths it writes are correct once it gets that far.
