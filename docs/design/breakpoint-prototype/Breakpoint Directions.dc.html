Two directions for the chrome

Both answer the same question — how does a tool frame content it does not own — and answer it differently. Each is shown on the identical canvas: three panes, one white page, one dark page, one saturated page, at 100% and at 25%.

1a

Gutter

chrome never touches content

The pane has no frame. It is a rectangle of somebody else's pixels sitting on our ground, separated by shadow alone. Every label, badge and state indicator lives outside the pane rectangle, in canvas gutters we control. Nothing is ever drawn on top of a page.

1b

Bezel

chrome is an opaque plate welded to the pane Recommended

The pane is set into a solid frame of chrome — a 24px header welded to the top and a 1px shell all round, one rounded unit. Legibility is bought with opacity rather than distance: the plate is always --bp-chrome, never translucent, so no page colour ever bleeds into a label. A 1px seam in --bp-border-seam keeps the plate from ever sitting directly against the page's own pixels.

Recommendation — 1b, with 1a's rule about overlays

1a has the purer answer to the central tension — chrome only ever sits on ground we own, so legibility is guaranteed rather than defended. It breaks on the second spike constraint. At 25% a detached label has no structural tie to its pane, and with six panes and a 100px mobile the labels collide and the canvas becomes a guessing game about which name belongs to which rectangle. It also spends horizontal room on gutters, which is the one resource this app is always short of.

1b buys the same legibility with opacity instead of distance, which costs nothing, and gets binding for free: a header clipped by its own pane cannot be misread. The risk is that a welded frame starts to look like a device mockup, so the bezel stays at 1px, square-ish, with no bevel, no drop of colour beyond the 3px identity tab, and no rounding above 4px.

Take one rule from 1a: state is expressed on the frame, not across the page. Error, crash, agent presence, off-screen and scheme mismatch are all rim-and-header events. The only thing permitted to draw over a pane is the transient inspect highlight, because it has to be registered to an element box to mean anything.
